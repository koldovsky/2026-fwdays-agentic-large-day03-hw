# Spec: Text orientation (horizontal / vertical) (#10533)

## Goal

Add a persisted `horizontal | vertical` text orientation on text elements so vertical labels render and edit correctly on the canvas (not only via ad hoc workarounds), with bounds and hit-testing aligned to the painted glyphs.

## Context

- Issue: [#10533](https://github.com/excalidraw/excalidraw/issues/10533)
- Current behavior: Text is laid out as horizontal lines (`wrapText` / `measureText`); `verticalAlign` only aligns those lines inside the box. Users can rotate the whole element with `angle`, but there is no first-class vertical character flow or a dedicated control in text properties.
- Expected: A new text property (name TBD, e.g. `textOrientation`) switches layout to vertical flow (one canonical direction, fixed in code—e.g. 90° vs −90°—and documented). The compact text properties UI exposes it when a text element is selected. JSON save/load and `restore` keep backward compatibility (missing field ⇒ horizontal).

## Component / Module

- `packages/element/src/types.ts` — `ExcalidrawTextElement` field and shared types
- `packages/element/src/newElement.ts` — default for new text elements
- `packages/element/src/textElement.ts` — `redrawTextBoundingBox` and related layout updates
- `packages/element/src/textMeasurements.ts`, `packages/element/src/textWrapping.ts` — measuring and breaking lines/glyphs for vertical mode
- `packages/element/src/renderElement.ts` — canvas rendering for `type: "text"`
- `packages/element/src/bounds.ts`, `packages/element/src/shape.ts` — selection bounds and geometric shape used for hit tests (update if width/height or local frame semantics change)
- `packages/element/src/transform.ts` — text create/duplicate paths that must copy the new field
- `packages/excalidraw/actions/actionProperties.tsx` — new action (same pattern as `changeTextAlign` / `changeVerticalAlign`)
- `packages/excalidraw/components/Actions.tsx` — `CombinedTextProperties` popover: add control next to existing text actions
- `packages/excalidraw/wysiwyg/textWysiwyg.tsx` — inline editor position, size, and input behavior for vertical text
- `packages/excalidraw/data/restore.ts` — migrate/defaults when the field is absent

## Non-goals

- Do NOT implement full vertical typesetting (e.g. CJK tategaki, mixed horizontal/vertical runs, ruby).
- Do NOT repurpose or remove `element.angle`; orientation is an additional layout mode unless the implementation explicitly proves a single combined model with independent UX.
- Do NOT change how existing scenes look unless a text element’s orientation is set to vertical.
- Do NOT expand scope to non-text element types.

## Acceptance Criteria

1. `ExcalidrawTextElement` includes the new orientation field with default `horizontal`; old files without the field load unchanged visually.
2. With a text element selected, the user can toggle horizontal vs vertical from the same compact text properties entry point used for font size / align (`CombinedTextProperties`).
3. Vertical mode renders on the interactive canvas with the chosen canonical direction; glyphs are not clipped by the element box and remain readable relative to scene axes.
4. Selection outline, resize/transform behavior, and pointer hit regions match the visible text for both orientations (update `bounds` / `shape` paths as needed).
5. Double-click to edit shows the wysiwyg editor in a stable position; editing does not corrupt `text` / `originalText` or drop caret positioning in a way that horizontal-only text regresses.
6. Behavior for text with `containerId` (bound to a shape or arrow) is explicitly defined: either fully supported with correct bounds or the orientation control is hidden/disabled and layout stays as today—document which and add tests.
7. Raster/SVG (or other) export paths used by the app show vertical text consistently with the canvas unless a path is out of scope—in which case list it and add a follow-up.
8. Existing tests pass (`yarn test`).
9. Build passes (`yarn build`).
